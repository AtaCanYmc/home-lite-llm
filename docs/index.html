Engineering Architecture

Reliable, Local-First AI Routing Pipeline

LiteLLM Proxy decouples development tools from individual API providers. All interactions standardize through a local reverse proxy with database-backed virtual keys and rate limit resilience.

01

Localhost-by-Default Ingress

Network port publications bind strictly to 127.0.0.1 by default. The PostgreSQL database operates exclusively on the internal bridge network, completely shielded from external interfaces.

02

Automated Fallback Routing

If an upstream provider encounters an outage or returns HTTP 429 rate limit errors, requests immediately failover to secondary targets (e.g. gpt-4o fails over to gemini-2.0-flash, then claude-3-5-sonnet).

03

Prompt and Key Privacy

Verbose prompt debugging is disabled. User messages, system instructions, and completion tokens are never dumped into host disk logs. Virtual keys are hashed before database persistence.

04

Host Storage Protection

Docker container logging enforces strict json-file rotation policies with 10 megabyte limits and 3 file backups, preventing disk exhaustion on high-throughput deployments.

JSON

Aider CLI Pair Programming

Set environment variables or launch with flags directly from your terminal.

Bash 
# Export connection parameters
export OPENAI_API_BASE="http://localhost:4000/v1"
export OPENAI_API_KEY="sk-your-secure-and-long-master-key-here"

# Launch Aider with desired model
aider --model openai/claude-3-5-sonnet

# Or with local Ollama model
aider --model openai/ollama-deepseek-r1

Python (Official OpenAI SDK)

Direct substitution of base_url in your client initialization.

Python 
from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:4000/v1",
    api_key="sk-your-secure-and-long-master-key-here",
)

response = client.chat.completions.create(
    model="claude-3-5-sonnet",
    messages=[
        {"role": "system", "content": "You are a helpful coding assistant."},
        {"role": "user", "content": "Explain connection pooling in PostgreSQL."},
    ],
)

print(response.choices[0].message.content)

Practical Answers

Frequently Asked Questions

Direct answers to common operational questions regarding LiteLLM Proxy configuration.

How do I authenticate requests to the gateway?
Requests require an HTTP header Authorization: Bearer <KEY>. You can use the root MASTER_KEY defined in your .env file, or generate fine-grained virtual keys with spend caps and model restrictions from the admin UI at http://localhost:4000/ui.
Can I run local models without paying for cloud API keys?
Yes. If you have Ollama, LM Studio, or vLLM running on your machine, you can make requests to ollama-llama3.3, ollama-deepseek-r1, or lmstudio-local immediately without supplying OpenAI or Anthropic API keys.
How do automated fallback chains trigger during rate limits?
When an upstream provider returns an HTTP 429 (Rate Limit Exceeded) or HTTP 5xx error, LiteLLM Proxy automatically catches the exception and reroutes the identical prompt to the next fallback model defined in config.yaml (e.g. gpt-4o reroutes to gemini-2.0-flash, then claude-3-5-sonnet). The client receives a successful response without failing.
Where are conversations and prompts stored?
The gateway is configured with production logging flags. User prompts and completion tokens are never stored to disk or container log files. The PostgreSQL database stores only virtual API key hashes, team metadata, and token usage counts for spend tracking.
